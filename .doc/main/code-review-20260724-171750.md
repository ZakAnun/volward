## 二、变更说明

### 变更概述

**变更主题**：
1. **浏览态缓存失效精准化**：`home_page.dart` 的 `_onSessionChanged` 新增 `_lastRefreshedSnapshotId`，用 `snapshot_id` 是否真变化来判定是否需要重算列导航缓存，替代此前"每次 session 通知都重算"的做法。
2. **checkpoint 子树合并语义修正**：`scan_snapshot_merge.dart` 的 `_replaceNodeAtPath` 命中目标节点时，`children` 从整体覆盖改为按 `path` upsert 合并（`_mergeChildrenByPath` + `_pickMoreComplete`），避免后台扫描的周期性 checkpoint 用尚不完整的视图覆盖掉已经展示出来的（预览/Wave 2 分片扫描）更完整数据。

**核心目的**：修复 2026-07-24 16:57 版审查报告（`code-review-20260724-165740.md`）中列出的两个 🟠 High 问题——"浏览期间高频全量缓存失效"与"checkpoint 无法区分已建节点但未扫完、Wave 2 点击优先在扫描早期之后基本失效"——确保渐进式扫描在浏览体验上真正做到不卡顿、不回退。

**变更类型**：Bug修复 + 性能优化

### 变更明细

#### 主题1：浏览态缓存失效精准化 (⚠️ → 已验证缓解)

**改动总结**：新增字段 `_lastRefreshedSnapshotId`，在扫描开始/结束分支同步写入当前 `snapshot_id`；第三分支（用户已钻取某层浏览）改为先比较 `_s.lastSnapshot?['snapshot_id']` 与该字段，仅在真正变化时才 `_invalidateSnapshotCaches()` + `_getDisplayTree()` + `refreshColumnChain`。

**行为对比**：

| 场景 | 原行为 | 新行为 |
| :--- | :----- | :----- |
| 扫描中，用户已钻取某层，纯进度 tick（无快照变化） | 每次 `notifyListeners()`（≈300ms/次）都 `_invalidateSnapshotCaches()` + 全树 `pruneTree`+`_sortTree`+聚合重算 | 判定 `snapshot_id` 未变，跳过缓存失效与重算，仅走通用 `setState(() {})` 的轻量 rebuild |
| checkpoint/peek 真正合并了新数据（`snapshot_id` 变化） | 同上（重算，但被淹没在同频率的无效重算里） | 正确检测到变化，执行一次缓存失效 + 树重算 + 导航保位 |

**关键改动点**：
- `_lastRefreshedSnapshotId` 在扫描开始（`!_prevScanning && _s.scanning`）与扫描结束（`_prevScanning && !_s.scanning`）分支也同步更新，避免下次进入浏览态时用陈旧 id 误判

#### 主题2：checkpoint 子树合并语义修正 (⚠️ → 已验证缓解，遗留一个可接受的边界情况)

**改动总结**：`_mergeChildrenByPath` 按 `path` 对旧/新 children 做 upsert：新数据独有的路径直接采纳（新发现）；旧数据独有的路径保留（checkpoint 尚未重新覆盖到）；两边都有时用 `_pickMoreComplete` 按聚合 `size_bytes` + `scanned` 挑更完整的一侧。

**行为对比**：

| 场景 | 原行为 | 新行为 |
| :--- | :----- | :----- |
| Wave 2 分片扫描已完整解析某目录，随后主扫描的下一次 checkpoint（该目录尚未被主扫描重新递归）到达 | 整体替换 `children`，已解析数据被清空/回退为空目录 | `_pickMoreComplete` 判定旧值 `scanned` 且体量更大，保留分片扫描结果 |
| checkpoint 尚未重新发现的已知子目录/预览子项 | 与其余 children 一起被整体清空 | 按路径缺失时保留旧值，不再丢失 |
| checkpoint 带来全新发现的子项 | 一并出现（整体替换本就包含） | 正常并入（新增路径直接采纳） |

**关键改动点**：
- `_pickMoreComplete` 仅用聚合 `size_bytes` 作为"更完整"的单一代理指标，未引入额外的完成度信号（Rust 侧仍未提供更精确的"该目录是否已被完整递归"标记，这是本次修复范围外的已知限制，参见风险评估）

## 三、影响面分析

**影响概述**：
- **对用户**：后台扫描期间钻取浏览不再出现每秒数次的全树重排卡顿；点击优先扫描出来的目录内容不会再被后续 checkpoint 悄悄"打回原形"。
- **对业务**：不改变最终 `Done` 快照的口径——`Done` 消息仍走独立的 `_loadSnapshotFromFile` 路径，不经过本次改动的合并逻辑，最终统计/删除闭环不受影响。
- **对系统**：`home_page.dart` 增加一个字符串字段的比较，开销可忽略；`scan_snapshot_merge.dart` 的合并从 O(1) 整体替换变为 O(子节点数) 的按路径 upsert，对典型目录（数十到数百个直接子项）开销同样可忽略。

**业务功能影响概述**：
1. 后台扫描期间浏览体验 — 影响高，兼容性完全兼容，验证结论：**已修复**（上版审查 High #1 关闭）
2. Wave 2 点击优先分片扫描的数据不被覆盖 — 影响中，兼容性完全兼容，验证结论：**核心回归已修复**；但"Rust 侧从不区分已建节点/未递归完成"的深层语义 gap 仍未解决（本次修复范围外，已在上版报告中说明，不阻塞本次合入）
3. 扫描过程中并发删除文件的展示一致性 — 影响低，兼容性完全兼容，风险点：见下方问题清单 Medium #1（自愈于扫描完成，不影响真实删除操作）

### 🟠 High（合并前必须修复）

*无* — 上一版审查的 2 个 High 问题（浏览态高频缓存失效、Wave 2 点击优先因整树替换失效）均已验证修复，`fvm flutter analyze` 无新增问题，`fvm flutter test test/`（34 个测试用例，含本次新增/修改的 3 个合并语义用例）全部通过。

### 🟡 Medium（建议修复）

1. **`_pickMoreComplete` 用聚合 `size_bytes` 做单一完整度代理，无法区分"体量变小=数据不完整"与"体量变小=文件被真实删除"** - `apps/volward/lib/scan_snapshot_merge.dart:159-168`
   - **问题**：`_pickMoreComplete` 的判定条件 `oldScanned && oldSize > newSize` 隐含假设"同一路径的体量只会随扫描推进增长"。但如果用户在扫描进行期间通过 Finder 或 Volward 自身的删除功能真实删除了某个已被 Wave 2 分片扫描完整解析（`scanned: true`）的子目录下的文件，主扫描随后重新递归到该目录、如实反映出更小的体量时，会被误判为"不完整的旧数据"而被丢弃，转而继续展示包含已删除文件的旧版本，直到该目录未来某次体量反超才会更新。不修复的后果是：用户在扫描过程中删除文件后，浏览界面可能短暂展示已经不存在的文件/过时的目录大小，造成"删除后数字没变"的困惑（不影响真实文件系统或最终 `Done` 快照的正确性，属于中间态展示问题）。
   - **建议**：现有修复范围内可接受此已知边界（自愈于 `Done`），若要进一步收紧，可在挑选"更完整"一方时，同时要求 `newChild` 不是来自权威来源（如最终快照）—— 即仅在两侧都来自"中间态 checkpoint"时才用 size 兜底，一旦有一方来自 `Done`/权威分片结果，直接采信该权威结果而不比较体量。当前代码尚未做这一区分，可作为后续小步优化。

2. **`on_checkpoint` 在 walk 线程同步克隆，随扫描进度增长成本递增（沿用自上版审查，本次未处理）** - `crates/volward-core/src/scan.rs:205-223`
   - **问题**：与上版审查报告一致，`entries.clone()` + `tree_builder.peek_snapshot()` 每次 checkpoint 都会克隆当前已发现的全部 `entries`/树并聚合，随着大目录扫描推进克隆体量线性增长，仍在主 walk 线程同步执行。本次修复未涉及 Rust 侧改动，该开销依旧存在，对于「体验上能否快速响应」这一问题而言，长时间全盘扫描后期仍可能因为该同步克隆造成 walk 吞吐轻微下降。
   - **建议**：维持上版建议——降低大树场景下的 checkpoint 频率，或将克隆/序列化移到独立线程异步执行。
